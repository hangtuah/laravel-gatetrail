# ADR 0006: Support Explicit Oracle Generated-Key Strategies

- Status: Accepted
- Date: 2026-07-28
- Decision owners: GateTrail maintainers

## Context

Six GateTrail tables use generated numeric primary keys:

```text
acl_roles
acl_permissions
acl_role_assignments
acl_permission_assignments
acl_role_permissions
acl_access_audits
```

Oracle can generate these keys with identity columns or with explicit
sequences and `BEFORE INSERT` triggers. Both approaches are valid, but database
ownership policies differ between organizations.

Some environments allow application-managed identity columns. Others require a
DBA to create named sequences and triggers so generated-key behavior remains
under database-owner control. GateTrail must support both environments without
changing its database-neutral schema manifest or its runtime mutation API.

`acl_assignment_locks` uses a composite primary key and does not need generated
key objects.

## Decision

The Oracle adapter will support two explicit, schema-wide generated-key
strategies:

```text
identity
sequence_trigger
```

`sequence_trigger` is the initial default. It matches GateTrail's Oracle 12c
Release 2 baseline, supports package-managed and DBA-managed provisioning, and
keeps every sequence and trigger name configurable.

The strategy is an Oracle physical-schema concern. It does not appear in the
canonical database-neutral manifest and does not change GateTrail's public PHP
API.

### One strategy per schema

An installed GateTrail schema uses one strategy for all six generated-ID
tables. Per-table mixing is not supported initially because it complicates
configuration, inspection, rollback, and operational documentation without a
demonstrated requirement.

### Identity strategy

With `identity`, each of the six primary-key columns uses `GENERATED BY DEFAULT
ON NULL AS IDENTITY`. Normal null inserts receive generated values, while
controlled migration or restoration can supply explicit IDs. GateTrail does
not create, name, inspect, or remove Oracle's internal identity sequence
directly.

The Oracle inspector validates the identity-column metadata rather than relying
on Oracle-generated internal object names.

### Sequence-trigger strategy

With `sequence_trigger`, GateTrail creates one configured sequence and one
configured `BEFORE INSERT` trigger for each of the six generated-ID tables.

Each trigger assigns the next sequence value only when the incoming primary key
is null:

```sql
IF :NEW.id IS NULL THEN
    SELECT configured_sequence.NEXTVAL INTO :NEW.id FROM dual;
END IF;
```

This preserves database-generated IDs for normal Eloquent inserts while
allowing controlled data migration or restoration to supply an explicit ID.

Application runtime code does not call `NEXTVAL`. The database generates the
value, and the supported Laravel-OCI8 driver must return the persisted key to
the Eloquent model.

### Provisioning and ownership

In package-managed mode, GateTrail migrations create the objects required by
the selected strategy.

In DBA-managed mode, a DBA, platform team, or database owner applies the
versioned Oracle artifact for the selected strategy. The application runtime
account does not require DDL privileges and does not create or repair missing
objects.

GateTrail publishes distinct, versioned Oracle install and rollback artifacts
for both strategies so an artifact never changes meaning based on runtime
configuration.

### Rollback order

Rollback follows physical dependencies:

1. drop package-owned triggers for `sequence_trigger`;
2. drop tables in reverse dependency order;
3. drop package-owned sequences for `sequence_trigger`.

Identity-owned internal objects are left to Oracle's table-drop behavior.
GateTrail never attempts to drop an Oracle-generated internal identity
sequence by name.

### Inspection and mismatch behavior

The selected strategy is part of the Oracle physical-schema contract.

- `identity` inspection requires identity metadata on all six ID columns and
  rejects configured sequence-trigger objects as satisfying that contract.
- `sequence_trigger` inspection requires all configured sequences and triggers
  and validates their association with the expected tables and ID columns.
- A missing, mixed, or mismatched strategy is reported as schema drift.
- Inspection is read-only and never repairs DBA-managed objects.

Neither strategy is advertised as verified until Eloquent key retrieval,
package-managed provisioning, DBA-managed provisioning, inspection, and
rollback pass against a supported live Oracle endpoint.

## Consequences

### Positive

1. GateTrail supports both application-managed and DBA-controlled Oracle
   environments.
2. The database-neutral schema manifest and public mutation API remain
   unchanged.
3. Versioned artifacts make the chosen physical strategy explicit during
   review and deployment.
4. Configurable sequence and trigger names respect organization-owned naming
   standards and the 30-character identifier limit.
5. Read-only inspection can distinguish a valid installation from a mixed or
   incomplete generated-key setup.

### Negative

1. The Oracle compiler, artifacts, inspector, and test matrix must cover two
   physical variants.
2. Consumers must choose a strategy before creating the Oracle schema.
3. Changing strategy after installation requires a separately designed schema
   migration; switching the configuration value alone is invalid.
4. Supporting explicit IDs in sequence-trigger mode requires tests that prove
   sequence-generated values do not overwrite supplied IDs.

### Neutral

1. `sequence_trigger` is an Oracle adapter default, not a package-wide
   requirement for other databases.
2. DBA-managed provisioning remains optional for consumers that control their
   own schema.
3. Sequence cache size, grants, tablespaces, and organization-specific storage
   clauses remain deployment concerns and may be adjusted in reviewed DBA
   artifacts.
4. The generated-key strategy does not define authorization, assignment, or
   audit behavior.

## Alternatives considered

### Support only identity columns

Rejected. It would exclude environments where DBAs require explicitly named
sequences and triggers and would discard an already accepted Oracle
operational requirement.

### Support only sequences and triggers

Rejected. It would unnecessarily prevent simpler identity-based provisioning
in organizations that allow it.

### Choose automatically from the Oracle version

Rejected. Both strategies are available on the supported Oracle baseline, and
version detection cannot infer an organization's ownership policy.

### Allow a different strategy for every table

Rejected for the initial design. No current use case justifies the additional
configuration, inspection, and rollback complexity.

### Put generated-key objects in the canonical manifest

Rejected. Sequences, triggers, and identity metadata are physical
vendor-adapter details; the logical requirement is only that the six tables
receive generated numeric IDs.

## Implementation requirements

- Add a validated Oracle strategy configuration with accepted values
  `identity` and `sequence_trigger`.
- Keep `sequence_trigger` as the initial default.
- Compile separate versioned install and rollback artifacts for both
  strategies from one canonical manifest.
- Use the existing configurable sequence and trigger names only for
  `sequence_trigger`.
- Keep every explicit identifier at 30 characters or fewer.
- Create parent tables before child tables and roll them back in reverse
  dependency order.
- Make sequence-trigger rollback remove triggers before tables and sequences.
- Never create generated-key objects for `acl_assignment_locks`.
- Fail closed when the configured strategy does not match inspected Oracle
  metadata.
- Add live Oracle tests for both strategies, both provisioning modes, Eloquent
  key retrieval, explicit-ID preservation, rollback, and schema drift.
