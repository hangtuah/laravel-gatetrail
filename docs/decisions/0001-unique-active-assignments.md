# ADR 0001: Serialize Equivalent Assignment Mutations

- Status: Accepted
- Date: 2026-07-27
- Decision owners: GateTrail maintainers

## Context

GateTrail preserves assignment history. Revoked and expired rows remain in their
assignment tables, while a later equivalent assignment creates a new row.

At the same time, GateTrail must prevent equivalent assignments from being
effective during overlapping periods. Application validation alone is
insufficient because two concurrent requests can both observe no conflict and
then insert duplicate rows.

A simple unique constraint on assignment identity is also insufficient:

- historical rows must remain;
- `NULL` uniqueness behavior differs between supported databases;
- whether an assignment is active changes as time passes;
- a future assignment can be valid when its period does not overlap another
  assignment;
- database support for partial, filtered, function-based, generated-column, and
  exclusion indexes is not uniform.

The solution must work on Oracle, MySQL, PostgreSQL, and SQL Server. SQLite must
provide equivalent behavior in automated tests.

## Decision

GateTrail will serialize mutations for each equivalent assignment scope through
a persistent coordination row. While holding the coordination-row lock, the
managed mutation service will check assignment-period overlap and perform the
assignment mutation and audit write in the same database transaction.

GateTrail will not use a time-dependent unique index on an assignment history
table as its portable correctness mechanism.

### Equivalent assignment scopes

Two assignments are equivalent when these values match:

| Assignment kind | Scope components |
|---|---|
| Role assignment | `subject_type`, `subject_id`, `role_id` |
| Direct permission assignment | `subject_type`, `subject_id`, `permission_id` |
| Role-permission assignment | `role_id`, `permission_id` |

Guard is enforced through the referenced role or permission and is not repeated
in the coordination key.

### Assignment periods

The effective period uses a half-open interval:

```text
[starts_at ?? assigned_at, expires_at ?? +infinity)
```

Two non-revoked assignments conflict when their effective periods overlap.
Touching boundaries do not overlap. For example, an assignment ending at
`10:00` does not conflict with one starting at `10:00`.

A revoked assignment is historical and does not block reassignment. An expired
assignment blocks only a new period that overlaps its historical effective
period.

This interval rule is stronger and more deterministic than evaluating only
whether both rows are active at the instant a mutation executes.

### Coordination table

The default table is:

```text
acl_assignment_locks
```

Minimum columns:

```text
assignment_kind
scope_hash
scope_key
created_at
updated_at
```

Required constraints:

```text
acl_asgn_locks_pk: PRIMARY KEY (assignment_kind, scope_hash)
```

All default object names remain within GateTrail's 30-character portability
limit.

`scope_hash` is a lowercase hexadecimal SHA-256 digest. It has a fixed length of
64 characters. `scope_key` stores the unhashed canonical key using portable
text/CLOB storage and is used to detect a theoretical hash collision after the
coordination row is read.

The coordination table does not require an auto-increment value, Oracle
sequence, or Oracle trigger.

### Canonical scope key

The canonical key must:

- include a format version and assignment kind;
- use the stored morph alias rather than an application class name;
- use the package-normalized string representation of subject identifiers;
- encode component lengths so delimiters inside values cannot create an
  ambiguous key;
- preserve case exactly after GateTrail's identifier normalization;
- be generated by one shared implementation for every database adapter.

Conceptual examples:

```text
v1 | role            | subject_type:user | subject_id:42 | role_id:7
v1 | permission      | subject_type:user | subject_id:42 | permission_id:9
v1 | role_permission | role_id:7          | permission_id:9
```

The actual serialized form will be covered by golden-vector unit tests. A
stored `scope_key` that does not match the key calculated for the same
`scope_hash` must fail closed with a dedicated collision exception.

### Mutation algorithm

Every managed assignment, scheduling, rescheduling, or revocation operation
must:

1. Normalize the scope and calculate its canonical key and hash.
2. Begin a database transaction.
3. Read the coordination row using a pessimistic write lock.
4. If it does not exist, insert it.
5. If another transaction wins the insert race, roll back the whole attempt and
   retry from step 2.
6. Verify that the stored canonical key matches the calculated key.
7. Lock and read equivalent assignment rows.
8. Apply the overlap and idempotency rules.
9. Persist the assignment mutation and its audit record.
10. Commit before cache invalidation and after-commit event dispatch.

Retries must be bounded. Exhaustion raises a package concurrency exception; it
must never silently allow a duplicate.

When one operation affects several scopes, coordination rows must be locked in
lexicographical order by `assignment_kind` and `scope_hash` to reduce deadlock
risk.

### Idempotency and conflicts

- Repeating an immediate assignment while an equivalent assignment is
  currently effective returns the existing assignment and does not create a
  new row.
- Requesting a new schedule that overlaps a non-revoked equivalent assignment
  raises a duplicate-assignment exception.
- A non-overlapping future period may be inserted as a separate assignment.
- Reassignment after revocation or expiry creates a new history row.
- Changing an existing period is a managed mutation and must acquire the same
  coordination lock before validating the replacement period.

The exact public result and exception types will be finalized in the public
mutation API ADR.

### Database adapters

The behavioral contract is identical for every supported database, but lock
acquisition and duplicate-key recovery may be adapter-specific.

| Database | Required behavior |
|---|---|
| Oracle | Unique primary key plus `SELECT ... FOR UPDATE`; retry the entire transaction after a coordination-row insert race |
| MySQL | Unique primary key plus an InnoDB row lock; retry the entire transaction after a duplicate-key or retryable deadlock failure |
| PostgreSQL | Unique primary key plus `SELECT ... FOR UPDATE`; retry the entire transaction because a constraint violation aborts the transaction |
| SQL Server | Unique primary key plus an update-compatible row lock; retry after duplicate-key, deadlock-victim, or other classified transient concurrency failures |
| SQLite | Use an adapter-controlled write transaction because `FOR UPDATE` is not available; preserve the same overlap and exception behavior in tests |

Adapters may use database-native insert-if-absent syntax when it is proven safe,
but this must not change the package-level behavior.

### Direct database writes

The coordination design guarantees concurrency safety for GateTrail's managed
mutation services. Direct inserts or updates to assignment tables bypass the
coordination protocol and remain unsupported, consistent with the package
specification.

Managed mutations fail closed when a coordination row's canonical key does not
match its stored hash. They do not repair the row automatically.

The `gatetrail:doctor` command performs read-only, best-effort checks for
overlapping assignments and missing, duplicated, malformed, or hash-mismatched
coordination rows. A clean result is not proof that managed services created
every row.

Full direct-mutation boundaries, diagnostic limitations, cache consequences,
and operational remediation are defined by
[ADR 0009](0009-direct-database-mutation-and-diagnostics.md).

## Alternatives considered

### Application validation without a database lock

Rejected because concurrent requests can both pass the overlap query before
either inserts.

### Unique index using `revoked_at`

Rejected because `NULL` handling differs by database and expiry is
time-dependent. It would also prevent legitimate history or permit different
invalid states depending on the database.

### A nullable `is_active` or `active_key` column

Rejected as the primary mechanism because its value becomes stale when time
passes unless a scheduler updates it. Authorization correctness must not depend
on a background job running at an exact time.

### Database-native temporal constraints

Rejected as the common mechanism. PostgreSQL range exclusion constraints can
represent non-overlapping periods directly, while the other supported
databases require materially different techniques. Requiring such features
would make schema behavior and operational requirements diverge.

Database-native constraints may be offered later as optional defense in depth
only if they preserve the same semantics.

### Serializable isolation without a coordination row

Rejected as the default because predicate-lock behavior, failure modes, and
operational cost differ across database engines. A concrete row provides an
explicit serialization point with narrower contention.

## Consequences

### Positive

- Correctness does not depend on wall-clock expressions inside an index.
- The same assignment-period rules apply across supported databases.
- Concurrent mutations for unrelated scopes do not block one another.
- Historical assignment rows remain immutable and queryable.
- The coordination mechanism is visible and auditable by a DBA.
- Oracle DBA-managed provisioning does not need an additional sequence or
  trigger for this table.

### Negative

- One persistent coordination row is stored for every assignment scope ever
  used.
- Assignment mutations require an additional locked lookup.
- Migrations and the schema manifest gain a seventh package table.
- Retry classification must be tested for every database driver.
- Direct database writes cannot receive the same guarantee.

### Operational notes

Coordination rows must not be pruned during normal operation. Removing a row
while another transaction uses the same scope could remove the serialization
point. Any future compaction tool requires its own ADR and an exclusive safety
protocol.

- include the table in Oracle DBA-managed schema validation.

## Verification

Before this decision is considered implemented, tests must prove:

- two concurrent identical immediate assignments create one assignment row;
- an exact immediate replay is idempotent;
- overlapping scheduled periods are rejected;
- adjacent scheduled periods are accepted;
- expired and revoked assignments remain in history;
- reassignment after expiry or revocation creates a new row;
- a hash mismatch fails closed;
- retry exhaustion fails closed;
- multi-scope locks use deterministic ordering;
- rollback removes the assignment and audit mutation but leaves no invalid
  coordination state;
- behavior is equivalent on Oracle, MySQL, PostgreSQL, SQL Server, and SQLite.
