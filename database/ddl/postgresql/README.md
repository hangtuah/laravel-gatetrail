# GateTrail PostgreSQL DBA artifacts

These artifacts provision GateTrail when database objects are managed outside
the application deployment account.

## Compatibility

- PostgreSQL 14 or later
- the built-in deterministic `C` collation

Release `0001` contains:

- `0001/install.sql` — creates the seven GateTrail tables and fifteen indexes
  in parent-before-child dependency order;
- `0001/rollback.sql` — drops the seven tables in child-before-parent order.

The committed artifacts use GateTrail's canonical table names without a schema
qualifier or custom prefix. Set the PostgreSQL `search_path` to the intended
schema before running the script. Environments that configure an explicit
schema, prefix or table name must generate and review matching DDL from the
same canonical manifest.

## Installation procedure

1. Confirm that the target database, schema and PostgreSQL version are correct.
2. Confirm that the `C` collation exists and none of the target objects exists.
3. Take the backup or recovery action required by the organization.
4. Stop application writes that could race with provisioning.
5. Run `0001/install.sql` as the database owner.
6. Confirm that every statement completed successfully.
7. Configure GateTrail with `database.provisioning` set to `dba`.
8. Run GateTrail's read-only PostgreSQL schema inspection to confirm the
   installed catalog matches the canonical manifest.

The install script intentionally has no `IF NOT EXISTS` clauses. An existing
object is a conflict requiring investigation, not a successful no-op.

PostgreSQL supports transactional DDL. Run the complete install in one explicit
transaction when the organization's deployment policy permits it, and roll the
transaction back if any statement fails.

## Verifying an installation

GateTrail ships a strict, read-only PostgreSQL schema inspector. It compares the
installed catalog with the canonical manifest and **reports** differences; it
never creates, alters, drops, repairs or locks an object, and every statement it
issues is a `SELECT` against `pg_catalog` and `information_schema`. It is safe
to run against a live database with the application's own read privileges.

It reports missing tables, unexpected or missing columns, wrong data types,
character lengths and nullability, missing or unexpected indexes and wrong
indexed-column order, missing or wrong primary, unique, foreign-key and check
constraints, wrong referenced tables or columns, `ON DELETE`/`ON UPDATE` drift,
generated-key drift, and any exact-comparison column that has lost its
deterministic `C` collation.

Two representations are accepted because both provisioning modes are canonical:

| Aspect | DBA-managed artifacts | Package-managed migrations |
|---|---|---|
| Generated key | `GENERATED BY DEFAULT AS IDENTITY` | `bigserial` (`nextval(...)` default) |
| Primary-key name | the manifest name, e.g. `acl_roles_pk` | PostgreSQL's `<table>_pkey` |

Both auto-assign an identifier and both still accept an explicitly supplied one.
`GENERATED ALWAYS AS IDENTITY` is reported as drift, because it rejects the
explicit identifiers GateTrail's own insert paths supply. Unique, foreign-key
and check constraints are explicitly named by both modes and must match the
manifest exactly.

Foreign keys are checked on three points DBAs most often change by hand:

- **Referenced object.** A foreign key's identity is its referenced schema,
  table **and** ordered columns. A key that resolves to an identically named
  table in another schema is reported as `foreign_reference_mismatch`, not
  accepted. The expected namespace is the schema being inspected — the
  configured one, or `current_schema()` when none is configured.
- **Referential action.** `ON DELETE`/`ON UPDATE` must be `RESTRICT` or
  `NO ACTION`. `CASCADE`, `SET NULL` and `SET DEFAULT` are reported as
  `foreign_rule_mismatch`, because each destroys assignment history.
- **Deferrability.** Every GateTrail foreign key must be `NOT DEFERRABLE`.
  `RESTRICT` and `NO ACTION` are only interchangeable at that setting:
  PostgreSQL can postpone a `NO ACTION` check to commit time, which `RESTRICT`
  cannot be postponed the same way, so `DEFERRABLE INITIALLY IMMEDIATE` and
  `DEFERRABLE INITIALLY DEFERRED` are both reported as
  `constraint_state_mismatch`.

PostgreSQL creates one index per primary-key and unique constraint, so a
correctly installed release `0001` schema carries **24** indexes: the manifest's
15 explicit indexes plus seven primary keys and two unique constraints. The nine
constraint-backed indexes are expected and are not reported.

Read-only inspection is verified against live PostgreSQL 14 for both
provisioning modes. It is schema evidence only: PostgreSQL application runtime
behaviour — mutations, resolution, auditing and concurrency — is not yet
verified.

## Runtime privileges

After installation, the application runtime account does not need `CREATE`,
`ALTER` or `DROP` privileges for GateTrail objects. Grant only the table and
identity-sequence privileges required by the application.

## Rollback procedure

`0001/rollback.sql` permanently drops GateTrail tables and their stored data.
Use it only as an explicitly approved removal or failed-installation recovery
step:

1. stop application traffic;
2. take and verify the required backup;
3. confirm that release `0001` is the installed schema;
4. run the rollback using the database-owner account;
5. verify all seven objects were removed.

The rollback script intentionally has no `IF EXISTS` or `CASCADE` clauses. A
missing object or unexpected dependency is reported instead of hidden.

## Reproducibility

The SQL files are generated from GateTrail's canonical schema manifest:

```bash
composer ddl:generate
```

Do not edit generated SQL manually. Automated tests compare the committed files
byte-for-byte with compiler output and fail when an artifact is stale.
