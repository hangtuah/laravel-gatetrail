# GateTrail Oracle DBA artifacts

These artifacts provision GateTrail when Oracle database objects are managed
outside the application deployment account.

## Compatibility

- Oracle Database 12c Release 2 or later
- A supported Laravel-OCI8 major matching the consuming Laravel major
- Unquoted portable identifiers of 30 characters or fewer

Release `0001` provides two generated-key variants:

```text
0001/identity/install.sql
0001/identity/rollback.sql
0001/sequence-trigger/install.sql
0001/sequence-trigger/rollback.sql
```

Choose exactly one variant for a GateTrail schema. Do not combine identity and
sequence-trigger objects.

## Choosing a generated-key strategy

Use `identity` when the database owner permits Oracle identity columns. The
artifact uses `GENERATED BY DEFAULT ON NULL AS IDENTITY` for the six generated
primary keys. Oracle owns the internal identity objects, and GateTrail does not
address their generated names.

Use `sequence-trigger` when generated keys must use explicitly named,
DBA-controlled objects. The artifact creates one sequence and one
`BEFORE INSERT` trigger for each generated-ID table. Each trigger requests
`NEXTVAL` only when the inserted ID is null.

`acl_assignment_locks` uses a composite primary key and has no generated-key
object in either variant.

## Canonical artifact scope

The committed artifacts use GateTrail's canonical table, sequence, trigger,
constraint, and index names without a schema qualifier or custom table prefix.

An environment that configures another schema, prefix, table name, sequence
name, or trigger name must generate and review matching DDL from the same
canonical manifest. Do not edit a committed canonical artifact in place and
continue describing it as reproducible.

## Installation procedure

1. Confirm the target Oracle database, schema owner, and supported version.
2. Select one generated-key strategy and configure GateTrail to match it.
3. Confirm that none of the target tables or strategy-owned objects exists.
4. Take the backup or recovery action required by the organization.
5. Stop application writes that could race with provisioning.
6. Run the selected `install.sql` using the approved database-owner account.
7. Confirm every table, constraint, index, and generated-key object completed
   successfully.
8. Configure GateTrail with `database.provisioning` set to `dba`.
9. Run GateTrail's read-only Oracle schema inspection before enabling
   application traffic.

The scripts intentionally contain no conditional create clauses. An existing
object is a conflict that requires investigation.

Oracle DDL causes implicit commits. Do not assume that wrapping the complete
script in a transaction makes installation atomic. If installation fails,
inspect the actual object state before deciding whether to resume or execute an
approved recovery procedure.

## Runtime privileges

After DBA-managed installation, the application runtime account does not need
`CREATE`, `ALTER`, or `DROP` privileges for GateTrail objects.

Grant only the data-access and execution privileges required by the consuming
application. GateTrail runtime code does not call a configured sequence
directly; sequence-trigger inserts obtain their value through the table trigger.
Final grants remain an organization-owned deployment decision.

## Rollback procedure

Each `rollback.sql` permanently drops GateTrail objects and their stored data.
Use it only as an explicitly approved removal or failed-installation recovery
step:

1. stop application traffic;
2. take and verify the required backup;
3. confirm release `0001` and the selected strategy;
4. run the matching rollback using the database-owner account;
5. verify that all expected objects were removed.

Identity rollback drops tables in reverse dependency order. Oracle removes the
internal identity objects with their owning tables.

Sequence-trigger rollback first removes GateTrail triggers, then drops tables
in reverse dependency order, and finally removes GateTrail sequences.

The rollback scripts intentionally contain no conditional drop clauses. An
incomplete or unexpected schema state must be reported rather than hidden.

## Reproducibility

All SQL files are generated from GateTrail's canonical schema manifest:

```bash
composer ddl:generate
```

Do not edit generated SQL manually. Automated tests compare the committed files
byte-for-byte with compiler output.

These artifacts prove reproducible compilation, not live Oracle compatibility.
Oracle support remains unverified until both strategies and both provisioning
modes pass the required live integration suite.
